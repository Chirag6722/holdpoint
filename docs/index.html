An agent's irreversible call stops here until it passes review.

Holdpoint sits between an agent and its MCP tools. Reads pass through. Calls that pay, delete, send or publish wait for automatic checks and an independent reviewer, or for a person to approve that exact call.

Did it work on a real agent?

Measured on 89 held-out task pairs from the AgentAbstain benchmark, run once. Each task has a near-identical twin where acting is wrong, so a gate that blocks everything scores zero.

The tested agent and judge are named in the measurement plan. These numbers cannot be compared with the benchmark's published leaderboard, because the judge and harness differ.

Paired accuracy did not rise, so this run shows no benefit.

11 pairs improved and 11 got worse (exact McNemar p = 1.0). Should-act accuracy fell 19.1 points. That is above the 10-point limit set in advance, so the reviewer costs more than we said was acceptable.

Should-stop tasks where an irreversible action ran: 25 of 89 without the gate, 6 of 89 with it. So the gate trades completed work for safety.

Source: every run. Rules fixed in advance: measurement plan.

What tuning changed

The first reviewer did worse than no gate at all, because it held too many legitimate calls. Reading its reasons led to two general changes: it now sees each tool's definition, and it must name a specific reason to hold. These 42 pairs were used for tuning, and the gain seen here did not carry over to the held-out pairs above.

Known limits

  • The labels are the boundary. A destructive tool labelled as a read runs freely.
  • The gate only sees MCP traffic. An agent with shell access or a raw API key can go around it.
  • The reviewer is a model, so it can be wrong or be persuaded.
  • A wrong hold stops legitimate work, which is why should-act loss sits beside every result.
  • Your host must give the gate the user's request. Without it, every commit is held.
